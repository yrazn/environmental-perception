# 环境感知项目实现流程与后续开发路线

## 1. 文档目的

本文档用于说明 `rescue_perception_py` 项目的定位、整体架构、端到端运行流程、各流程对应的代码文件及核心算法，并明确当前已经完成、已经实现但尚未接入、以及后续仍需实现的内容。

项目是一个面向隧道火灾和应急救援机器人的多传感器环境感知原型，采用纯 Python 与 NumPy 实现。核心架构是“传感器独立检测、目标级后融合、统一跟踪、风险评估和安全决策”。

当前实现适合算法验证、合成场景演示和接口设计，还不是可直接部署到真实救援机器人的生产系统。2026-09-02 的代码完善已接入 YAML、运行模式、时间同步入口和巡检输出，并修复若干正确性问题。

主要入口如下：

## 3. 整体实现流程

```text
仿真数据 / 实际传感器 / ROS 2
              │
              v
      SyncedSensorData 同步帧
              │
              v
阶段0：传感器质量评估、退化模式、动态权重
              │
              v
阶段1：RGB / 热成像 / LiDAR / 雷达 / 烟雾 / 气体独立检测
              │
              v
阶段2：人员 / 火源 / 车辆目标级融合
              │
              v
阶段3：统一语义跟踪
              │
              v
阶段4：传感器坐标到 map 坐标转换
              │
              v
阶段5：场景级风险评估
              │
              v
阶段6：停车、限速和人工确认策略
              │
              v
阶段7：PipelineOutput -> 终端 / Web / ROS 2
```

主管线由 `PerceptionPipeline.spin_once()` 实现。每次调用处理一个 `SyncedSensorData`，并返回一个 `PipelineOutput`。

## 4. 核心数据模型

代码文件：`rescue_perception/types.py`

### 4.1 `SyncedSensorData`

表示完成近似时间同步的一帧输入，包含：

- RGB 图像；
- 热成像显示图和逐像素温度矩阵；
- 3D LiDAR 点云；
- 4D 毫米波目标；
- 气体和颗粒物读数；
- 温湿度；
- 里程计；
- 各传感器同步误差。

主管线只处理完整同步帧，不直接管理零散传感器消息。

### 4.2 `Detection3D`

是检测层的统一输出格式，保存类别、置信度、来源传感器、位置、尺寸、速度、协方差、温度和扩展属性。RGB、热成像、LiDAR 和雷达检测结果都转换成该结构后再进入融合层。

### 4.3 `TrackedObject`

是融合和跟踪后的统一目标。状态向量为：

```text
[x, y, z, length, width, height, vx, vy]
```

同时包含全局目标编号、多传感器来源位掩码、确认状态、丢失帧数、地图坐标、火源热区半径、车辆占道比例和风险属性。

### 4.4 `EnvironmentQuality` 与 `SensorWeights`

`EnvironmentQuality` 保存环境可见度、烟雾、温湿度以及各传感器可信度。`SensorWeights` 保存 RGB、热成像、LiDAR、雷达、2D LiDAR 和气体在当前模式下的动态权重。

### 4.5 `PipelineOutput`

主管线最终输出，包括：

- 跟踪目标列表；
- 感知状态和退化模式；
- 动态权重；
- 环境质量；
- 烟雾估计；
- 气体风险；
- 综合环境风险；
- 安全策略；
- 热风险等级。

## 5. 阶段0：质量评估、退化状态和动态权重

### 5.1 相关文件

- `rescue_perception/perception_pipeline.py`
- `rescue_perception/management/quality_monitor.py`
- `rescue_perception/management/degradation_manager.py`
- `rescue_perception/config.py`
- `rescue_perception/types.py`

### 5.2 传感器质量评估

`QualityMonitor.assess()` 分别计算：

- RGB：亮度、对比度和梯度清晰度；
- 热成像：有效温度像素比例、中心区域均匀性和窗口梯度；
- LiDAR：有效点比例、近场散射、最大探测距离和衰减；
- 雷达：目标数量稳定性和 RCS 一致性；
- 气体：高湿度导致的可信度修正。

主管线的 `_health_from_quality()` 将连续可信度转换成健康状态：

```text
可信度 < 0.10：FAILED
可信度 < 0.30：DEGRADED
其他：OK
```

### 5.3 退化状态机

`DegradationManager` 实现四级状态：

```text
CLEAR -> LOW_VISIBILITY -> HEAVY_SMOKE -> PERCEPTION_DEGRADED
```

状态转换主要参考烟雾指数、RGB/LiDAR/热成像/雷达可信度、环境亮度和气体传感器状态。状态恢复采用比进入更严格的条件，并通过三秒切换锁避免短时间振荡。

### 5.4 动态权重

系统先读取当前模式的基础权重，再根据传感器可信度降权。重烟时降低 RGB 与 LiDAR，提高毫米波和气体；完全退化时将 RGB 与 3D LiDAR 权重置零，以毫米波、2D LiDAR 和气体为主。

当前阶段0使用上一帧烟雾估计和上一帧 LiDAR 质量，这是为了打破当前帧质量评估和烟雾估计之间的循环依赖，但也产生一帧决策延迟。

## 6. 阶段1：单传感器独立检测

### 6.1 RGB 检测

代码文件：`rescue_perception/detectors/rgb_detector.py`、
`rescue_perception/detectors/yolo_backend.py`

处理流程：

1. 通过 `DetectionBackend` 调用模型或仿真后端；
2. 对火焰、人员、车辆应用不同置信度阈值；
3. RGB 严重失效且处于重烟模式时抛弃视觉火焰结果；
4. 对连续帧位置稳定的火焰提高置信度；
5. 根据烟雾掩膜或后端属性计算烟雾概率、覆盖率和质心。

当前已实现 Ultralytics YOLO 基准后端，默认采用官方 `yolo11n.pt` COCO
权重，可识别人员和常见车辆。合成演示仍默认使用
`rescue_perception/sim/backends.py` 中的 `SyntheticRgbBackend`。火焰、烟雾、
人员姿态和可靠三维深度仍需专用模型及传感器标定。

### 6.2 热成像检测

代码文件：`rescue_perception/detectors/thermal_detector.py`

处理流程：

1. 局部中值修复异常温度像素；
2. 使用最近若干帧估计背景温度；
3. 使用自适应阈值分割热点；
4. 进行八连通区域提取；
5. 计算面积、周长、圆形度和边缘梯度；
6. 与历史热点匹配，计算温升率、面积增长率和持续时间；
7. 分类为明火、疑似火源、热设备、温暖表面、热异常或人体热源；
8. 转换为 `Detection3D` 并给出 0～4 级热风险。

主要阈值形式为：

```text
T_threshold = T_background + max(30, 3 × background_std)
```

### 6.3 LiDAR 点云处理

代码文件：`rescue_perception/detectors/lidar_cluster.py`

处理流程：

1. 距离直通滤波；
2. 体素下采样；
3. RANSAC 地面平面拟合；
4. 地面与非地面点分离；
5. 基于空间哈希的欧氏聚类；
6. PCA 拟合三维包围盒和朝向；
7. 根据长、宽、高判断人员候选、车辆或通用障碍物；
8. 计算有效点比例、近场散射、最大距离和衰减。

在退化模式下，程序会增大体素尺寸和聚类容差，以适应稀疏点云并减少计算量。

### 6.4 毫米波跟踪

代码文件：`rescue_perception/detectors/radar_tracker.py`

雷达内部状态为：

```text
[x, y, vx, vy, ax, ay]
```

处理流程包括静态杂波过滤、运动预测、距离关联、卡尔曼更新、轨迹生命周期维护，以及根据 RCS、速度和微多普勒进行人员/车辆候选分类。模块还保存最近目标距离，供风险和安全策略使用。

### 6.5 烟雾估计

代码文件：`rescue_perception/detectors/smoke_estimator.py`

烟雾指数融合图像、PM、LiDAR 衰减和 CO 四项证据：

```text
S = w_image × F_image
  + w_pm    × F_pm
  + w_lidar × F_lidar
  + w_co    × F_co
```

其中图像项由烟雾概率和覆盖率组成，PM 与 CO 使用相对历史基线的增长，LiDAR 项由有效点减少、近场散射和探测距离缩短组成。最终结果经过指数移动平均平滑，并映射为清晰、轻烟、重烟和盲区等级。

### 6.6 气体风险

代码文件：`rescue_perception/detectors/gas_risk.py`

模块分别对 CO、CO2、O2、CH4 和 H2S 分级，综合风险取各气体的最大风险等级。同时根据 CO/CO2 上升、O2 下降和温度上升趋势判断火灾特征，并判断爆炸风险和窒息风险。

## 7. 阶段2：目标级后融合

### 7.1 通用关联

代码文件：`rescue_perception/fusion/association.py`

实现匈牙利最小代价匹配、最大代价门控和二维 IoU。人员融合使用位置、类别、温度和时间构造关联代价。

### 7.2 人员融合

代码文件：`rescue_perception/fusion/person_fusion.py`

融合 RGB 人员、热人体、LiDAR 人形聚类和毫米波目标。程序根据动态权重计算融合置信度，并通过人体温度范围、LiDAR 人体尺寸和雷达微多普勒验证候选。重烟时降低 RGB 贡献，提高热成像和毫米波证据的重要性。

### 7.3 火源融合

代码文件：`rescue_perception/fusion/fire_fusion.py`

融合 RGB 火焰、热成像热点、气体火灾特征和爆炸风险。多源一致时输出已确认火源，证据不足时保留火源候选，并根据最高温度计算高温禁区半径。

### 7.4 车辆融合

代码文件：`rescue_perception/fusion/vehicle_fusion.py`

融合 RGB 车辆、LiDAR 大尺寸聚类和雷达高 RCS 目标。模块保留事故状态，并根据车辆宽度与车道宽度计算占道比例，区分部分阻塞和完全阻塞。

## 8. 阶段3：统一语义跟踪

代码文件：`rescue_perception/fusion/semantic_tracker.py`

处理流程：

1. 对已有轨迹进行匀速预测；
2. 按人员、火源和车辆语义组匹配；
3. 匹配成功时执行卡尔曼更新；
4. 未匹配且置信度足够的候选创建新轨迹；
5. 连续命中达到阈值后设为已确认；
6. 短时未命中时继续预测；
7. 超过最大丢失帧数后删除；
8. 合并空间上过近的同类别轨迹。

该模块为所有融合目标分配统一的全局 `track_id`。

## 9. 阶段4：语义定位

代码文件：`rescue_perception/fusion/semantic_localizer.py`

模块维护 RGB、热成像、LiDAR 和雷达各自到地图坐标系的 4×4 变换矩阵：

```text
P_map = T_sensor_to_map × P_sensor
```

同时使用旋转矩阵构造雅可比矩阵，将协方差传播到地图坐标。当前默认变换全部为单位矩阵，启动脚本没有读取真实标定或 ROS TF，因此演示中的传感器坐标实际被直接视为地图坐标。

## 10. 阶段5：环境风险评估

代码文件：`rescue_perception/management/risk_assessor.py`

综合风险因子包括：

- 热风险；
- 气体风险；
- 最近障碍距离；
- 车辆占道；
- 目标深度失效比例；
- RGB 退化程度；
- 运动目标存在情况。

不同退化模式使用不同权重。正常模式较重视 RGB 和深度，重烟模式主要依赖热成像、气体和障碍物。之后执行最大风险兜底，例如四级热风险、三级气体风险和两米内障碍都会强制提高综合风险分数。

模块还生成火源确认、发现人员、车辆堵塞、气体危险、感知丢失和可见度盲区事件。

## 11. 阶段6：安全策略映射

代码文件：`rescue_perception/management/risk_assessor.py`

主要映射规则为：

| 条件 | 输出策略 |
| --- | --- |
| 外部急停 | 立即急停，速度为 0 |
| 四级热风险、感知完全丢失、障碍小于 1 米 | 停车等待 |
| 三级热风险、高环境风险、障碍小于 3 米 | 20% 低速并要求确认 |
| 二级热风险、低可见度、障碍小于 5 米 | 50% 限速 |
| 其他 | 正常运行 |

安全结果包含安全等级、速度上限、必需动作和是否需要人工确认。

代码文件：

代码文件：`rescue_perception/io/ros2_bridge.py`

## 13. 时间同步流程

代码文件：`rescue_perception/io/sensor_sync.py`

`SensorSync` 为每种传感器维护时间戳队列，以最新消息时间为参考，在各自容差内寻找最近消息并组装 `SyncedSensorData`，同时记录同步误差。

主管线现提供 `spin_from_sync()`，可以直接从 `SensorSync` 拉取同步帧。Demo 和 Web 仍直接使用仿真场景生成的完整同步帧；真实传感器适配器和 rosbag 回放仍待实现。

## 14. 巡检类检测模块

代码文件：

- `rescue_perception/detectors/crack_segmenter.py`
- `rescue_perception/detectors/water_detector.py`
- `rescue_perception/detectors/facility_inspector.py`

现有能力包括：

- 裂缝分割掩膜转长度、宽度和位置；
- 积水分割结果转积水区域和深度等级；
- RGB/热图设施异常后端接口；
- 对应的合成后端。

这些对象已接入 `spin_once()`，并受 `inspection/rescue/minimal` 模式控制。结果通过 `PipelineOutput.cracks`、`water_regions`、`facility_anomalies` 输出，也进入 Web API 和仪表盘。当前仍只有合成后端，尚未接入真实巡检模型和地图级缺陷生命周期管理。

## 15. 配置机制

代码和配置文件：

- `rescue_perception/config.py`
- `config/perception_master.yaml`
- `config/degradation.yaml`

实际运行支持 `PerceptionConfig.from_yaml()`。终端 Demo 和可视化启动脚本默认读取两个 YAML，并支持 `--config`、`--degradation` 和 `--mode` 覆盖。配置采用递归合并，局部参数不会覆盖未修改的默认子项。

此外，`DegradationManager.get_behavior()` 已实现模式对应的最大速度和自主运行建议，但主管线没有调用；实际停车和限速由 `RiskAssessor.map_to_safety()` 独立决定。

## 17. 代码问题与修复状态

### 17.1 RGB 清晰度单位不一致（已修复）

原实现将 `sharpness` 限制在 0～1，却使用 `sharpness > 80` 判断清晰环境。现已统一为归一化阈值，并增加清晰环境回归测试。

### 17.2 独立 PM 输入未使用（已修复）

主管线现优先读取 `SyncedSensorData.pm`，缺失时回退到气体复合读数中的 PM25/PM10，并增加独立 PM 输入测试。

### 17.3 Marker 位置计算不完整（已修复）

Marker 现直接读取目标地图位置，`pose_map` 的平移部分也会写入变换后的目标坐标。

### 17.4 非单位坐标变换可能重复作用（已修复）

坐标变换现作用于进入统一跟踪器之前的临时融合测量，持久轨迹始终保存在 map 坐标，避免对 coasted 轨迹重复应用外参。

### 17.5 配置文件不生效（已修复）

现已实现 YAML 加载、递归配置合并、启动参数和 `inspection/rescue/minimal` 模式控制。

### 17.6 巡检后端设置后没有被调用（已修复主管线接入）

巡检模块现按运行模式进入主管线，输出写入 `PipelineOutput`、Web API 和仪表盘；真实巡检模型仍待接入。

### 17.7 ROS 2 包装未完成

现有包装没有实际订阅、同步、TF、QoS、自定义消息和异常恢复，也未被测试覆盖，不能直接作为生产节点使用。

### 17.8 风险实现存在无效变量（已修复）

已删除未使用的 `max_factor`；原有热、气体、障碍和占道风险兜底规则保持不变。

### 17.9 传感器超时未纳入健康判断（已部分修复）

同步误差现在进入 `SensorHealth`，超过阈值会标记同步退化或 TIMEOUT。真实接入后仍需基于接收时钟补充 `last_update_age`、驱动诊断和重连状态。

### 17.10 双层跟踪职责需要澄清

人员融合内部维护轨迹，随后统一语义跟踪器再次跟踪。需要明确两层轨迹的职责和 ID 映射，否则真实场景中可能出现轨迹重复、状态不一致或延迟增加。
